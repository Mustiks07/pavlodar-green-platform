5. ОБЩИЙ КОНТРАКТ
Canonical API: contracts/openapi.json. Canonical domain: contracts/domain.schema.json.
Спецификация имеет version 1.0.0; данные организатора не считаются уже полученными.
GPT реализует DTO и сервер по контракту, Claude генерирует TypeScript-клиент.
CI сравнивает реализованный OpenAPI с canonical по обязательным полям, типам,
nullable, enum, ошибкам, auth и статусам. Побайтовое сравнение генераторов не требуется.
Контрактные fixtures валидируются JSON Schema; MSW отвечает только этими fixtures.
Запрещены any-DTO, локальные переименования enum и отдельные единицы на фронтенде.

6. ИЗМЕНЕНИЕ КОНТРАКТА
Оформить docs/adr/ADR-<id>.txt: проблема, вариант, изменение, совместимость,
затронутые задачи, JSON до/после, миграция и проверка. Получить acknowledgement
в handoff другого агента. Для нового additive поля: обновить schema/fixtures,
сгенерировать клиент, выполнить проверку, затем подключить UI.
Breaking change: новая major API либо согласованное атомарное изменение обеих частей
до выпуска. Не удалять поля, пока существующий клиент ещё использует их.
Конфликт трактовки решается исходным ТЗ и acceptance criteria, а не личным вкусом агента.

7. ЦИКЛ КАЖДОЙ ЗАДАЧИ
Выбрать work package с выполненными depends_on. Указать владельца и базовый SHA.
Реализовать вместе с негативными состояниями, миграциями и относящимися тестами.
Подключить к реальному сервису. Приложить команды, результаты и evidence paths.
В handoff указать что изменено, контракт, файлы, commit SHA, риски, блокеры и next step.
Другой агент выполняет review по своей стороне. Один аккаунт GitHub не заменяет
независимого человеческого approval; если защита ветки его требует, не обходить её.
Done означает интегрированный и проверенный результат, а не «код написан».

8. ЧАСТОТА СОВМЕСТНЫХ ПРОВЕРОК
После foundation: auth + город + источник данных из API в UI.
После map/import: опубликованный слой появляется на карте с исходными метаданными.
После scenario: редактирование -> серверная ревизия -> расчёт -> восстановление страницы.
После planning: бюджет/вода -> допустимый портфель -> выбранный участок -> 3D.
После assistant/export: одинаковая версия расчёта в карточке, чате и PDF/Excel.
После execution: задания -> осмотры -> исходные когорты и замены -> факт против прогноза.
Не накапливать отдельные «готовый frontend» и «готовый backend» без этих соединений.

Владелец данных и эксперт подтверждают расчётную пригодность, не агент по умолчанию.
