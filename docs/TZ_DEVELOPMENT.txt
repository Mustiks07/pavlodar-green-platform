ТЕХНИЧЕСКОЕ ЗАДАНИЕ НА РАЗРАБОТКУ ПЛАТФОРМЫ ОЗЕЛЕНЕНИЯ ГОРОДА ПАВЛОДАРА
Версия 1.0.0. Дата 29.10.2026. Репозиторий AIFESTHackathon2026/team-vtiposhnik.
Заказчик исходной задачи: городской акимат. Разработка: GPT и Claude, аккаунт Mustiks07.

## 01 Назначение документа и границы готовности
Документ задаёт продукт, поведение, архитектуру, данные, алгоритмы, совместные интерфейсы и проверяемые условия готовности. Требования обязательны для обеих частей одного приложения. Конечный результат - работающая система с постоянным хранением, реальными вычислениями, импортом, разграничением доступа, картой, 3D, отчётами и контролем работ. Сроки хакатона не являются основанием исключать функции.
Исходное ТЗ организаторов от 22.10.2026 является основанием обязательного функционального охвата. Дополнительные требования этого документа фиксируют целевой продукт пользователя. Указанные здесь эксплуатационные показатели, лимиты и workflow - проектные требования, а не заявления, что исходный заказчик их уже подтвердил.
На дату документа организаторские данные не получены. Разработку платформы разрешено начинать. Приёмка экологических прогнозов, точных посадочных мест и результатов на данных организатора зависит от data gates в planning/data_requests.json. Незакрытый gate нельзя скрыть синтетическим набором. Разработка функции и подтверждение её применимости к Павлодару - отдельные состояния.
Нормативная территория - ГОРОД ПАВЛОДАР. Временный контур OSM way/170089891 не считается подтверждённой официальной границей. Любые областные климатические или правовые источники должны иметь явно указанную применимость; областная статистика не становится городской автоматически.
ТЗ не заменяет согласованный дендроплан и разрешение на работы. Специалист принимает окончательное решение; статус approved в системе означает внутреннее утверждение, не автоматическое получение государственного разрешения.

## 02 Результат для пользователя и продуктовый охват
Продукт объединяет три уровня: городская программа инвестиций; проект озеленения конкретного участка; выполнение ухода и проверка результата. Между уровнями сохраняются одни объекты, версии, расчёты и источники. Пользователь не перепечатывает цифры между модулями.
На городском уровне специалист видит дефицит зелени, проблемные территории, социальные объекты и качество данных; выбирает цели, веса и лимиты; получает несколько допустимых программ работ с объяснением компромиссов. На уровне участка выбирает растения, размещение, уход и сценарий; сравнивает стоимость, ожидаемую приживаемость и эффект. После утверждения получает задания, фиксирует осмотры, видит план против факта.
Полезные демонстрационные сценарии обязательны: изменение доступной воды перестраивает программу; перенос дерева в 3D выявляет конфликт и меняет расчёт; сравнение двух вариантов сохраняет одинаковую камеру; чат раскрывает источник конкретного числа; смерть исходного дерева не исчезает из статистики после замены.
Система включает деревья, кустарники, многолетники и травянистое покрытие. Допускает вариант без новых посадок, например восстановление почвы или улучшение ухода. Нельзя сводить результат к максимальному количеству самых дешёвых деревьев.
Автоматическая закупка, подача заявлений в государственные системы, распознавание лиц, персональные данные жителей, автоматическое разрешение вырубки и обучение универсальной foundation-модели не входят в эту версию. Запрос на такую функцию оформляется отдельно, без вытеснения обязательных модулей.

## 03 Роли и основные пользовательские маршруты
viewer читает доступные городские слои, утверждённые проекты и разрешённые отчёты. specialist создаёт и редактирует сценарии, импортирует в карантин, запускает расчёты, составляет программу, ведёт задания и осмотры. admin управляет пользователями, справочниками, правами источников, публикацией наборов и внутренним утверждением. Доступ определяется сервером, включая фоновые задания и скачивание файлов.
Внутренние сети и точные служебные данные могут иметь dataset.access_level=restricted; viewer не получает их геометрию или скрытые атрибуты. Роль specialist не даёт автоматического доступа ко всем restricted-наборам: проверять grants пользователя/группы. Public-портал не включать по умолчанию.
Маршрут A: вход -> обзор города -> проблема -> участок -> подбор -> сценарий -> расчёт -> сравнение -> внутренняя проверка -> отчёт. Маршрут B: импорт -> проверка -> разрешение конфликтов -> публикация версии -> пересчёт зависимых результатов. Маршрут C: бюджет и ресурсы -> программа -> участки -> задания -> осмотр -> сравнение исходов. Маршрут D: вопрос в чате -> вызов модуля -> результат со ссылкой на ту же версию сценария.
Сохранённая ссылка восстанавливает город, выбранную зону, сценарий и ревизию, вид карты и фильтры, но не обходит права. Обновление страницы не теряет сохранённый план. Изменения в несохранённом редакторе обозначаются; пользователь может отменить их или сохранить новую ревизию.

## 04 Архитектура и технологические решения
Выбран модульный монолит для API и предметной логики плюс отдельные процессы вычислительных воркеров. Модули имеют явные интерфейсы и не читают чужие таблицы через UI. Такой вариант сохраняет транзакции и единые правила при разработке двумя агентами, а тяжёлые расчёты масштабирует независимо. Выделение микросервисов допускается позже по измеренной потребности через ADR, а не ради количества сервисов.
Клиент: React, TypeScript strict, Vite; TanStack Query для серверного состояния; Zustand для состояния редактора/камеры; React Router; React Hook Form и Zod для формы. MapLibre GL JS для карты, Three.js для сцены и размещения объектов. Проектный старт совместимой пары - MapLibre 5.20.0 и Three 0.180.0, проверенной локальным стендом. Остальные точные версии фиксируются lockfiles в WP-00 после compatibility/security проверки. Не использовать latest в воспроизводимой сборке.
Сервер: Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2, psycopg 3, Alembic. PostgreSQL с PostGIS. Python-пакеты domain/calculations/geo независимы от HTTP. OR-Tools CP-SAT для дискретного выбора программ, pvlib для солнца, GDAL/rasterio и Shapely/pyproj для подготовки пространственных данных. Параметры solver и округления входят в версию расчёта.
Фоновые задания: Celery + Redis, долговременное состояние Job и transactional outbox в PostgreSQL. Redis не является единственным источником статуса или результата. Отдельные очереди import, analysis, export и physical; ограниченные concurrency, память и timeout. Тяжёлая физика не выполняется в HTTP-процессе.
Файлы: S3-совместимый адаптер; для локальной разработки файловый адаптер с тем же API допустим, production использует утверждённое хранилище. Не закреплять конкретный облачный сервис без требований размещения. Базовая карта PMTiles с HTTP Range; изменяемые слои - MVT из PostGIS и детализация объектов через API; растры - COG с тайловым сервисом.
Аутентификация: OIDC Authorization Code, серверный BFF хранит токены провайдера, браузер получает HttpOnly Secure SameSite=Lax session cookie. Production провайдер - Keycloak или согласованный совместимый OIDC; local Compose может включать Keycloak realm. Не писать собственную систему хранения паролей. Для mutating cookie-запросов проверять Origin и CSRF-токен. Протокол провайдера закрыт сервером, frontend не хранит refresh-token в localStorage.
LLM через адаптер провайдера: JSON schema tools, таймаут, лимит стоимости/токенов, журнал вызовов без секретов. Поставщик и модель выбираются по тестовому набору и правилам размещения. RAG первоначально PostgreSQL full-text; embeddings добавляются через pgvector при доказанном улучшении поиска. Нельзя делать работоспособность основных расчётов зависимой от LLM.
Развёртывание: контейнеры Linux, Docker Compose, reverse proxy с TLS, миграционный job, health/readiness endpoints. Наблюдаемость: структурированные JSON-логи, request_id/trace_id, OpenTelemetry, метрики Prometheus-совместимого формата. Конкретные образы фиксируются digest/версией в реализации. GPU - необязателен для базовой платформы; подтверждённого права на NVIDIA-сервер нет.

## 05 Структура репозитория и границы модулей
apps/web - React-приложение. packages/ui - дизайн-система. packages/map - адаптер MapLibre, Three.js и редактора. packages/api-client - сгенерированные типы и транспорт, без ручной правки generated-файлов.
services/api - маршруты, auth, сериализация, use cases. services/worker - запуск фоновых use cases. packages/domain - сущности и инварианты. packages/calculations - правила, стоимость, survival, care, priority, ecosystem. packages/geo - метрические операции и пространственная подготовка. packages/optimization - составление модели CP-SAT и интерпретация результата.
migrations - единственная цепочка Alembic. infra - compose, proxy, storage adapters, backup/restore, metrics. contracts - canonical OpenAPI/JSON Schema, fixtures, семантика. data/manifests - ссылки и лицензии, без гигантских растров в Git. tests - contract, integration, e2e, performance, scientific fixtures. docs/adr - решения и изменения. coordination - статус и handoffs.
GPT владеет сервером, данными, вычислениями, инфраструктурой и canonical-контрактами; Claude - клиентом, картой и UX. Изменения shared manifests и схем выполняет один владелец. Подробный процесс находится в TEAM_PROTOCOL.txt и обязателен обоим агентам.

## 06 Общие типы и числовые соглашения
ID - UUID. Внешние source_id сохраняются отдельно от внутренних идентификаторов. API snake_case; локальные TS имена могут быть idiomatic, но сериализатор и generated DTO сохраняют контракт. Версия API /v1; версия контракта SemVer. Datetime RFC3339 UTC; календарные даты YYYY-MM-DD; городской display_timezone Asia/Almaty, текущее UTC+5, не фиксировать смещение навсегда в логике.
GeoJSON - RFC7946, EPSG:4326 и порядок longitude, latitude. API принимает 2D-геометрию; высота в отдельном поле с датумом/источником. Геометрию хранить с SRID, проверки топологии и единиц выполнять до публикации. Геометрические расчёты Павлодара в EPSG:32643; geodesic-проверки для контроля. Никогда не считать градусы метрами.
Money - decimal string в KZT с двумя знаками, например "12500.00"; БД numeric, Python Decimal. Стоимость считать с большей внутренней точностью, round half up до 0.01 на строку, итог - сумма округлённых строк. Налог отдельной строкой/полем по явно указанному режиму; ставку НДС не зашивать в код. Отрицательная цена запрещена, отрицательная корректировка - отдельный тип документа.
Вероятность - число 0..1, UI показывает %. Риски в процентных пунктах не смешивать с относительным изменением %. Пригодность/приоритет - 0..100. Площадь м², длина м, вода м³, ET0/осадки мм, температура °C, углерод т CO2/год для потока. Каждая оценка содержит unit, horizon, method_version, input_snapshot_id, provenance и status.
Неизвестное: value=null, status=unavailable, reason_code и required_inputs. Нулевое значение допустимо только как известный результат. В общих Metric допускаются measured, estimated, synthetic, unavailable; источник организатора не отдельный статус достоверности. Если интервал не рассчитан обоснованным методом, lower/upper=null и qualitative_confidence, а не произвольный доверительный диапазон.
Canonical JSON schemas определяют структуры обмена. Пространственная валидность, суммы долей, монотонность survival, право доступа и согласованность версий дополнительно проверяются предметной логикой - JSON Schema сама этого не гарантирует.

## 07 Предметная модель и хранение
City хранит рабочую/официальную границу, timezone, CRS, статус подтверждения. Zone - стабильная идентичность участка; ZoneVersion - неизменяемая геометрия, назначение и ссылки на источники. Район, квартал и участок - разные уровни, не определять их только из названия. Все городские сущности имеют city_id; запрещено случайное смешение данных городов.
Dataset и DatasetVersion: владелец, лицензия, URL/файл, checksum, observed_at, valid_from/to, метод, точность, разрешение, CRS, access_level, schema_mapping, quality_report, статус. Исходный объект хранится неизменённым. Структурированные observation имеют значение, единицу, глубину/период и sample geometry. SoilObservation нельзя сводить к одному усреднённому pH без указания способа агрегации.
GreenObject: стабильный объект, тип, геометрия, таксон если известен, дата посадки, крона/высота если известны; GreenObservation - датированный осмотр, метод, состояние. BuildingFeature хранит measured/recorded/estimated height_basis и исходную этажность. PopulationObservation агрегированная, без персональных данных. Restriction и RuleVersion содержат нормативный источник, применимость, период действия, параметры и подтверждение эксперта.
PlantTaxon/PlantVariant: латинское и русское названия, вид/сорт, ярус, требования и диапазоны, риск аллергии/токсичности, рост, крона/корни, источники. StockItem отделён: поставщик, размер/возраст саженца, количество, дата наличия, цена/валюта, подтверждение. Биологический таксон не равен товару питомника.
RateVersion/CoefficientVersion/ModelVersion: значения и единицы, условия применимости, доказательство, дата действия, экспертное согласование. Scenario - именованная ветвь проектирования; ScenarioRevision - immutable payload с конкретными входными версиями, посадками, лимитами и правилами. CalculationSnapshot - результаты и полный manifest для повторения, без перезаписи старых данных.
Program и ProgramRevision фиксируют лимиты, цели, варианты участков и выбранный набор. CandidateAlternative хранит согласованные посадки+уход+стоимость+прогноз; выбирать части разных альтернатив как одну нельзя. WorkOrder, WorkCompletion и Inspection фиксируют назначенное, выполненное и наблюдаемое отдельно. PlantingCohort и ReplacementLink связывают первоначальные и замещающие посадки без потери истории.
Job, OutboxEvent, ExportArtifact, ChatSession, ChatMessage, ToolInvocation, AuditEvent, UserGrant завершают модель. PK/FK, check constraints, unique (source_id,dataset_version), индексы city/status/time, GiST geometry, transactional timestamps. Soft archive применяется к используемым объектам; удаление данных, на которые ссылается утверждённая ревизия, запрещено. Конкретный ERD и миграции - WP-01 по этим инвариантам.

## 08 Приёмка данных и конвейер импорта
F-DATA-01. Принимать GeoJSON, SHP zip, KML и CSV координат. CSV имеет preview, выбор колонок, кодировки/разделителя и CRS; SHP требует .shp/.shx/.dbf и определённую CRS, .prj желательно. При неизвестной CRS требовать выбор, не угадывать молча. Архив не может писать вне временного каталога, содержать symlink или бесконтрольно распаковываться.
F-DATA-02. Этапы: upload -> quarantine -> validation -> mapping -> review -> publish или reject. Публикация только admin; specialist может подготовить. Слой не виден как production до publish. Импорт атомарен на уровне версии: читатели используют старую опубликованную версию до успешного switch pointer.
F-DATA-03. Проверять тип/структуру, размеры, координаты, самопересечения, дубли, геометрию вне города, пустые значения, единицы, даты, диапазоны pH/процентов, ссылки на каталог, пересечения зон где они недопустимы. Отчёт содержит severity, object/source_id, код, объяснение, предложенное исправление и ссылку на карту. Warning не должен превращаться в silent correction.
F-DATA-04. Конфликт источников решать по задаче, методу, точности и дате; хранить обе исходные версии и решение оператора. Устаревший организаторский слой не получает автоматически приоритет над свежим проверенным измерением. Не сливать деревья только по совпадению координат без допуска и проверки идентичности.
F-DATA-05. Начальные лимиты: файл до 500 MB, распакованный архив до 2 GB, до 1 000 000 объектов, максимум 2 импорта одновременно. Лимиты конфигурационные и покрыты тестами; большие источники проходят отдельный batch pipeline. Сеть загрузки источников имеет allowlist, timeout и запрет внутренних адресов для URL-импорта; пользовательский URL не выполняется как команда.
F-DATA-06. На публикации формировать immutable manifest, spatial indexes, simplified tiles, statistics и lineage; выпустить событие dataset.published. Изменение источника делает зависимые расчёты stale, а не переписывает их. Пользователь явно выбирает повторный расчёт на новых входах. Неизменяемые версии доступны для воспроизводимости по правам.

## 09 Карта города и геопространственная аналитика
F-MAP-01. Основные слои: граница, районы, дороги/водоёмы/здания, участки, почвы, существующая зелень, ограничения, население/социальные объекты, проблемы, приоритет, предлагаемые посадки, качество данных. Легенда и цветовая шкала обязательны; каждая активная шкала имеет единицу, период и источник.
F-MAP-02. Выбор готового участка, рисование/редактирование полигона и поиск адреса. Поиск использует локальный индекс адресов из разрешённых источников либо согласованный провайдер через backend. Публичный Nominatim не использовать как массовое autocomplete. Нечёткий результат предлагает выбор, а не переносит карту в область вместо города.
F-MAP-03. Карточка зоны: площадь, назначение, существующее покрытие, данные почвы, окружение, сети/пробелы, качество источников, проблемы. Геометрическое пересечение, буферы и площадь считают серверные модули. Частичное покрытие почв выводится долей площади, а не одним недостоверным значением.
F-MAP-04. Для города MVT/PMTiles, bbox+zoom фильтрация, кластеризация точек и уровни детализации. Полный GeoJSON всех зданий не скачивать при каждом открытии. Детальная geometry по выбранному объекту. Запросы при pan отменять/дедуплицировать; stale ответ старого viewport не заменяет новый.
F-MAP-05. Базовые тайлы, glyphs, sprites, JS и CSS доступны локально в профиле offline-city. Холодный запуск без интернета проверяется после очистки browser cache, а не только повторным открытием. Слой конфиденциальных сетей не включать в публичный PMTiles или service-worker cache.

## 10 Выявление проблемных зон
F-PROB-01. Выявлять дефицит площади зелени и зелени на жителя, плохое состояние насаждений, почвенные риски, тепловую нагрузку при пригодных данных и отсутствие защитного озеленения рядом с дорогами/школами/больницами/жильём. Каждая проблема имеет тип, severity high/medium/low, rule_version, входные свидетельства, рекомендацию и confidence.
Нормативный порог, статистический порог и экспертный порог различать. Доля озеленения считается площадью объединения пригодных полигонов, не суммой перекрытий. Площадь крон, наземное зелёное покрытие и доступное общественное озеленение - отдельные метрики. По территории с неизвестным населением per_capita=null.
Состояние дерева нельзя уверенно установить по отсутствию OSM-тега. Спутниковый NDVI после маски облаков - признак покрытия, не автоматический диагноз болезни каждого дерева. Температура поверхности Landsat не температура воздуха; в карте и отчёте эти названия не взаимозаменяемы.
F-PROB-02. Таблица и карта имеют общие фильтры по типу, остроте, району, качеству, периоду. Карточка проблемы раскрывает точное условие срабатывания. Исключение оператором требует причины и не удаляет первичное наблюдение. При недостаточных данных вернуть data_gap, а не «проблем нет».

## 11 Каталог и подбор растений
F-PLANT-01. Каталог поддерживает поиск, фильтры, карточку вида/сорта, источники характеристик и доступные посадочные материалы. Минимальные признаки: зимостойкость/климат, засуха, ветер, свет, почва/pH/засоление/влага, загрязнение и реагенты, высота/крона/корни, ярус, аллергенность/токсичность, календарь ухода, рост и эффект. Неизвестный признак хранить unknown.
F-PLANT-02. Сначала evaluate_hard_constraints: запрещённые виды, назначение детской/больничной территории, сети и отступы, допустимая геометрия, критические климатические/почвенные ограничения. Нарушивший запрет вариант excluded независимо от суммы баллов. Неизвестный safety-critical признак даёт requires_review и не проходит к утверждению.
F-PLANT-03. После фильтра score=100*sum(w_i*s_i)/sum(w_i) по опубликованной версии правил. s_i лежит в 0..1. Для неполных некритичных признаков вернуть coverage и confidence, применить заранее зафиксированную стратегию missing policy; нельзя молча улучшать результат исключением неудобных факторов. Top-N включает score contributions, причины и ссылки на данные. Равные баллы сортировать детерминированно по стабильному ID.
F-PLANT-04. Предлагать ярусный состав, приблизительное количество и схему по доступной площади. Расстояния и размеры рассчитывать по версии правил и выбранному возрастному горизонту. Границы взрослой кроны и корневой зоны учитывать отдельно. Лимит доли вида настраиваемый по пространственному уровню; правило 10/20/30 не применять автоматически ко всем маленьким участкам.
F-PLANT-05. Пользователь может исключить/заменить вид, зафиксировать конкретный объект или состав. Перегенерация уважает lock. При невозможности совместить lock, бюджет, воду и ограничения вернуть конкретные причины infeasible. Не перемещать закреплённое дерево скрытно ради красивой картинки.

## 12 Сценарии и единый вычислительный граф
F-SCEN-01. Scenario имеет имя, zone_id, status draft/in_review/approved/archived и current_revision_id. Любая правка создаёт ScenarioRevision с parent_revision_id и входным manifest. PATCH сценария не меняет утверждённый snapshot. Status transition требует прав, проверок и reason; вернуть 409 при недопустимом переходе.
F-SCEN-02. Браузер получает ETag ревизии. Создание следующей ревизии требует If-Match. При гонке вернуть 412 с current_revision_id; UI предлагает сравнить и перенести изменения, не делает silent last-write-wins. Автосохранение дебаунсить, но визуально различать editing/saving/saved/failed/conflict.
Граф: опубликованные входы + нормативы -> context зоны -> допустимые места/виды -> состав и уход -> стоимость и survival -> рост и экологический эффект -> сравнение/городская оптимизация -> отчёт. Детерминированное ядро не вызывает LLM. Нельзя зациклить care -> survival -> reserve -> budget -> care без явного алгоритма выбора согласованной альтернативы.
Для предварительного сравнения строить законченные альтернативы: каждая содержит посадки, уход, затраты, риск и эффект. Оптимизатор выбирает целые альтернативы, затем может инициировать ограниченную повторную генерацию с новым request_id. Указывать критерий остановки, число итераций и best feasible result; не обещать математический глобальный оптимум эвристической расстановки.
F-SCEN-03. Snapshot включает версии входов, правил, расценок, коэффициентов, модели и кода, seed, единицы, rounding, solver settings, вычислительное окружение, warnings, provenance и output_hash. Кеш-ключ по canonical normalized inputs и всем зависимостям; TTL не заменяет invalidation. Старые результаты остаются доступны с меткой stale.
F-SCEN-04. Сравнение 2-3 ревизий показывает одинаковые горизонты/единицы, различия входов, total cost, care/water, survival, эффект и data quality. Несопоставимые периоды подсветить. «Эконом», «сбалансированный», «максимальный эффект» - цели генерации, а не заранее зашитые красивые карточки с фиксированными цифрами.

## 13 Смета и стоимость жизненного цикла
F-COST-01. Статьи: посадочный материал, подготовка/грунт/дренаж/удобрения, доставка и посадка, полив/уход 1-3 года, ожидаемые замены, отдельный резерв риска, применимые налоги. Каждая строка содержит quantity, unit, unit_price, rate_version_id, formula, subtotal, year и источник. Ставки редактирует admin с созданием версии; существующие сметы не меняются.
Стоимость посадки = сумма материалов + подготовка + работы + доставка. Стоимость ухода по году = сумма плановых операций. Ожидаемая стоимость замен считается по когортам с вероятностью гибели и временем замены, не как первоначальное количество, умноженное на одинаковый процент каждый год. Замена включает нужные работы/доставку/уход и учитывается только один раз.
Резерв риска сверх математического ожидания должен иметь policy и confidence method: фиксированный согласованный процент или квантиль сценарной модели, с явным названием. Общая засуха/болезнь может коррелировать потери; независимые Bernoulli не являются универсальным допущением. Система не выдаёт ожидаемый бюджет за гарантированный предел.
Для 5/10/20-летнего эффекта дополнительно показывать lifecycle_cost на сопоставимом горизонте либо честно сообщать, что denominator содержит лишь 3 года. Дисконтирование использовать только с указанной ставкой, базовым годом и одинаковым подходом к альтернативам. Тенге/т CO2 требует определённого периода потока, не смешивать один год и накопленный эффект.
F-COST-02. При отсутствующей цене хотя бы существенной строки total_status=incomplete, known_subtotal отдельно, total=null. UI может показать расчётную цену из явно выбранного сценарного источника с маркировкой estimated/synthetic; нельзя считать пропуск нулём. Стоимость живого дерева через 3 года - вторичный показатель, не единственная цель программы.

## 14 Приживаемость и проверка модели
F-SURV-01. Для каждой группы посадок возвращать S1,S2,S3 в 0..1. При модели условных рисков h_t: S_t=product(1-h_k). Для одной исходной когорты S1>=S2>=S3; replacement cohort считается отдельно. Основные входы: вид/сорт, размер и возраст саженца, почвы, освещённость, ветер/температура, дорожная нагрузка, уход/полив и дата посадки.
Первый допустимый механизм при нехватке исходов - экспертная модель с опубликованными коэффициентами, доменом применимости и qualitative confidence. Синтетическое обучение может проверять pipeline, но не служит доказательством точности на Павлодаре. Метод model_kind=expert_rules/ml/hybrid и calibration_status видны на карточке и в экспорте.
F-SURV-02. Риски объяснять факторами и ссылками на входы. Число «минус N процентных пунктов» допускается только если вычислено определённым методом при фиксированных остальных входах; это модельное сравнение, не доказанный причинный эффект вмешательства. SHAP/feature importance не называть причинным влиянием.
F-SURV-03. Система предлагает альтернативный вид, улучшение почвы и режим ухода и пересчитывает сценарий. Контрфактическая рекомендация должна быть физически выполнимой, учитывать стоимость, воду и правовые ограничения. При отсутствии модели для горизонта вернуть unavailable, а не экстраполировать 3-летнюю вероятность линейно на 20 лет.
Калибровка: датированные осмотры и исходы, неизвестное наблюдение не является гибелью. Разбиение по территории и времени исключает утечку; feature availability соответствует моменту планирования. Отчёт содержит размер выборки/классы, ROC-AUC где применим, Brier score, calibration plot, интервал неопределённости, ошибки групп и сравнение baseline. Исходное ТЗ допускает экспертное подтверждение вместо целевой тестовой метрики; точный эксперт и процедура - DR-04.
F-SURV-04. В UI отдельно N_initial, expected_alive_initial, observed_alive_initial, replacements_alive и total_alive. Доля осмотренных и дата обязательны. Нельзя повышать «приживаемость первоначальной посадки» подсадкой новых растений или исключением пропавших наблюдений.

## 15 Уход вода и выполнимость работ
F-CARE-01. План по месяцам и сезонам содержит полив, подкормки, обрезку/формовку, мульчу, защиту от болезней/вредителей и подготовку к зиме. Каждая операция имеет период, условие запуска, объём, единицу, трудозатраты, необходимые ресурсы, цену и источник агрономического правила. Химические препараты не рекомендовать без утверждённого справочника и разрешённых условий применения.
Объём полива не равен ET0 напрямую. Пример параметризации для территории: net_mm=max(0, ET0_mm*Kc-effective_rain_mm-soil_storage_available_mm); gross_m3=net_mm*irrigated_area_m2/(1000*efficiency). Коэффициенты Kc, эффективность, площадь и допустимый дефицит имеют источники; схема для приствольных лунок может использовать отдельную экспертную норму. Не переносить нормы газона на дерево без обоснования.
F-CARE-02. Проверять месячные и годовые лимиты воды, рабочие часы бригад, число выездов, сезонное окно и доступность участка. Отображать перегрузку и возможные решения. Снижение воды пересчитывает и уход, и связанный прогноз, но не уменьшает их скрыто до допустимости. Одновременно согласованный план может быть infeasible при недостаточных ресурсах.
F-CARE-03. Календарь фильтруется по району, участку, операции, сроку, исполнителю и статусу. Работы сохраняются и могут быть экспортированы. Изменение текущей погоды не переписывает утверждённый план: формируется предложение корректировки с версией. Фактический расход хранится отдельно от планового.

## 16 Приоритет и оптимизация городской программы
F-PRIO-01. Для каждой зоны индекс 0..100 по дефициту зелени, населению/застройке, социальным объектам, тепловой/воздушной нагрузке, почвенной готовности и эффекту/затратам. Каждый фактор нормализуется заранее определённым методом с зафиксированными bounds/референсом. Веса >=0, сумма после нормализации 1; при всех нулевых весах вернуть 422.
Показывать вклад факторов, полноту входов, sensitivity и причину изменения позиции. Отсутствующие показатели нельзя приравнивать к благополучию. Потребность и техническая готовность выводить раздельно, чтобы сложные бедные зеленью участки не исчезали из программы лишь из-за дорогой подготовки.
F-PRIO-02. Изменение весов в UI пересчитывает индекс по опубликованным агрегатам; сервер подтверждает результат и сохраняет версию. Браузерный preview допускается только по тем же специфицированным агрегатам и формуле с тестом равенства; authoritative результат всегда серверный. Не запускать полный микроклимат при каждом движении ползунка.
F-PROG-01. Дискретные переменные x_(zone,alternative) выбирают не более одной альтернативы на участок. Ограничения: капитальный бюджет, расходы по годам, вода по месяцам/годам, часы бригад, stock availability, обязательные/исключённые участки, locks, разнообразие и заданный социальный охват. В альтернативы включается «не выполнять» или подготовительный вариант, если он допустим.
Цель - согласованная взвешенная полезность по normalized benefit vector, с весами и референсом в manifest. Показать несколько Pareto-подобных компромиссов при разных целях. Не суммировать CO2, градусы и людей без нормализации и явной функции полезности. Не выдавать простой sorted priority за оптимальное распределение бюджета.
F-PROG-02. CP-SAT получает целочисленные ресурсы: деньги в тиынах, воду в заданном дискретном масштабе, труд в минутах. Веса полезности масштабировать с документированной погрешностью; ресурсные округления консервативны. Проверить overflow, двойной учёт, недопустимые отрицательные лимиты и дубли участков.
F-PROG-03. Ответ solver_status=optimal/feasible/infeasible/timeout/unknown, objective, best_bound/gap где применимы, время и ограничивающие факторы. Feasible при таймауте можно показать с меткой «лучшее найденное», не «оптимальное». При infeasible предложить диагностические конфликтующие лимиты; не обещать минимальный unsat core, если метод его не вычисляет.
F-PROG-04. Утверждённая ProgramRevision фиксирует выбранные ScenarioRevision и календарь. Перестройка создаёт новую версию с diff: какие участки добавлены/исключены, стоимость и потерянная/полученная польза. Ручное изменение перепроверяет все ограничения.

## 17 Экологический эффект и научные границы
F-ECO-01. На 5/10/20 лет сохранять годовой поток поглощения CO2, пыль/загрязняющие вещества, выработку кислорода, изменение температуры воздуха, задержание дождевой воды, площадь зелени и зелень на жителя. У каждого показателя method, коэффициенты, возраст/крона, сценарий ухода, survival, assumptions и статус. Обязательный показатель с недостаточными входами остаётся в интерфейсе как unavailable с причиной, а не исчезает.
CO2: различать stock и annual sequestration. Рост кроны/биомассы считается по обоснованной возрастной кривой и ожидаемым живым когортам. Не переносить американский коэффициент в Казахстан как локально измеренный. CO2/year и cumulative CO2 имеют разные имена и единицы. Кислород не трактовать как самостоятельную величину, которую можно независимо монетизировать и сложить с тем же углеродным эффектом без проверки двойного учёта.
Пыль/загрязнение: вид, листовая поверхность, сезонность и экспозиция; не выдавать постоянный коэффициент на дерево без области применимости за измерение. Осадки: сценарий дождя, перехват/инфильтрация и покрытие; нельзя обещать сокращение стока по любой погоде одним числом. Площадь зелени - union геометрий соответствующего типа, без суммирования перекрывающихся крон.
F-ECO-02. Тень, температура поверхности, температура воздуха и тепловой комфорт - отдельные метрики и легенды. Для воздуха выбран кандидат InVEST Urban Cooling: землепокров, canopy/shade, albedo, ET0/Kc, reference air temperature/UHI и пространственные параметры; требуется проверка входов и локальная калибровка. Если достаточно увлажнения не обеспечено, не оставлять исходное допущение модели молча.
F-ECO-03. Для детального радиационного комфорта использовать валидированный адаптер SOLWEIG/Tmrt при наличии DSM/геометрии, погоды и радиационных входов. UTCI требует соответствующих дополнительных входов и валидной реализации. Результат тени из графического движка не считается результатом SOLWEIG или моделью воздуха.
F-ECO-04. До/после рассчитывать на одинаковой территории, погодном сценарии, периоде и единицах, сохраняя baseline. Не сравнивать разные годы без обозначения климатической разницы. На графиках различать прогноз, наблюдение и неопределённость. Оценочные результаты явно обозначаются в UI и PDF/Excel.

## 18 Редактор 3D и проверка размещения
F-3D-01. Карта 2D и сцена 3D используют одинаковые object_id и authoritative геометрию. Масштаб города: упрощённые экструдированные здания и агрегированная зелень. Масштаб участка: подробные кроновые объёмы, стволы, кустарники, покрытия и зоны ограничений. Instancing, LOD, frustum culling и лимит texture memory обязательны; не рендерить весь город подробными GLTF.
F-3D-02. Отображать origin/height_basis каждого здания и дерева. Известная высота, этажность с допущением и visual placeholder различимы. Условная высота 6 м допустима только в явно обозначенном обзорном режиме, не в утверждённом точном shadow report. Overture может дополнить геометрию после проверки покрытия/качества, не считается готовым источником точных высот по умолчанию.
F-3D-03. Редактор поддерживает добавить/переместить/повернуть/заменить/удалить объект проекта, массовое выделение, snap, undo/redo и lock. Preview может быть локальным; после завершения операции сервер проверяет границу, коллизии, сети, расстояния и ограничения вида. Некорректная позиция подсвечивается и не получает approved. Изменения существуют в scenario revision, не правят городской исходный слой.
F-3D-04. Ползунок роста использует возрастную модель и year=0/1/3/5/10/20; календарная дата и время управляют положением солнца отдельно. Если нет кривой роста - доступна только условная визуализация с подписью, аналитические цифры не меняются по художественной анимации. Зимний/летний режим листвы связан с источником фенологии/сценарием.
F-3D-05. Синхронизированное сравнение before/after, вид с уровня человека, фиксированные viewpoints, выделение объекта на карте из таблицы и обратная связь. Объекты за пределами viewport могут отбрасывать тень; вычислительная область включает буфер, рассчитанный для выбранной высоты солнца и геометрии. Ночью solar shadow отсутствует, при низком солнце ограничение области явно сообщается.
F-3D-06. Геометрические тени: pvlib solar position; детерминированный метод пересечения/растеризации с размером ячейки и точностью. GPU shadow map - интерактивный preview; для площади/часов тени нужен отдельный проверенный аналитический результат. Ориентация осей, локальный origin и metre-to-Mercator scale проверяются контрольными задачами. Нельзя показывать высокоточные сантиметры из метрового источника.
F-3D-07. Режим degraded graphics отключает дорогие эффекты, сохраняет редактирование и численные результаты. При отсутствии WebGL2 предложить 2D-режим с понятным сообщением. Photogrammetry/3D Tiles через Cesium является расширением по ADR при реальных входных данных, не обязательным вторым рендерером базовой версии.

## 19 Задания исполнение и фактический результат
F-EXEC-01. Из approved revision создавать WorkOrder: участок, операция, окно дат, плановые объёмы/единицы, ресурс, ответственная служебная группа, источник плана. Статусы planned/assigned/in_progress/completed/cancelled; transition audit. Частичное выполнение хранится WorkCompletion и не закрывает весь заказ автоматически.
F-EXEC-02. Фиксировать фактические объёмы, дату, замечания и подтверждение; изображение может быть приложением с ограничением доступа и без обязательной геолокации граждан. Изменения выполненных работ - correction record с автором/причиной, не незаметная перезапись истории. Финансовый акт закупки и оплата не имитируются этим модулем.
F-EXEC-03. Inspection содержит дату, объекты/когорту, метод, observed_alive/dead/unknown, состояние, покрытие обследования, источник и экспертный статус. Возраст и исходы отсчитываются от planting_date. ReplacementLink хранит причину, исходный объект, дату замены и новую когорту. Одна замена не может одновременно считаться исходным выжившим деревом.
F-EXEC-04. Dashboard план/факт показывает расход, выполнение ухода, охват осмотров и исходную приживаемость. Сравнение с прогнозом только на сопоставимых объектах/горизонте и при достаточном наблюдении. До наблюдений показывать «нет осмотров», не 100% success. Обновление модели требует нового model_version и review, не незаметного обучения на каждом клике.

## 20 Диалоговый ассистент
F-AI-01. Чат получает city/zone/scenario_revision контекст, язык и права пользователя. Доступные инструменты: найти зоны/объекты, получить контекст, подобрать растения, подготовить изменение сценария, запустить расчёт/оптимизацию, получить результат и сформировать отчёт. SQL, shell, произвольный URL и чтение секретов инструментами чата не предоставлять.
F-AI-02. Инструмент возвращает structured facts с fact_id, value/unit/horizon, source_refs, calculation_id и revision_id. Ответ связывает утверждения с этими facts; проверять не совпадение цифры в тексте, а тип, единицу, объект и версию. Пользователь открывает ссылку и видит соответствующую карточку/формулу. Выдуманный источник или отсутствующая запись недопустимы.
F-AI-03. Retrieval отфильтрован по доступу до передачи модели. Документы и tool output считаются недоверенными данными; инструкции из них не меняют системные права/поведение. Не передавать полные restricted-слои внешнему LLM; allowlist разрешённых полей и журнал egress. Уточнить допустимость облачного провайдера в DR-07.
F-AI-04. Изменяющий инструмент создаёт proposal и показывает diff; пользователь применяет его к указанной ревизии. Proposal требует текущего If-Match и проверок сервера; не применять к другой версии после задержки ответа. Утверждение программы/работ не выполняется автоматически из фразы модели. Результаты read-only доступны сразу.
F-AI-05. Ассистент сообщает, какие входы отсутствуют и какие действия доступны. При отказе провайдера обычный интерфейс продолжает работать. Chat status queued/streaming/completed/failed/cancelled; tool calls идемпотентны. Ограничить максимальные шаги, токены, время и стоимость на запрос; зависший агент не создаёт бесконечную цепочку jobs.
F-AI-06. Оценочный набор минимум 40 заданий: корректные действия, отсутствующие данные, неверные единицы, скрытые слои, конфликт ревизий, вредоносный текст источника, timeout, вопрос о другой зоне. Для структурированных числовых claims точность ссылок 100% на фиксированном наборе; сложное естественное объяснение дополнительно оценивает специалист. Нельзя обещать универсальное отсутствие ошибок вне набора.

F-EXP-01. PDF и Excel для участка/варианта и городской программы. Титул, город/зона, версия, дата, автор служебного решения, источники, карта, состав, смета, survival 1/2/3, уход, priority, eco 5/10/20, качество и ограничения. В Excel отдельные листы summary, quantities, rates, costs, care, survival, ecosystem, sources; машинные единицы и читаемые подписи.
F-EXP-02. Экспорт ссылается на frozen calculation snapshot, а не запускает незаметный пересчёт текущих справочников. Пока job не finished, ссылка отсутствует; failure возвращает причину. Файлы имеют checksum, expiry для download token, access rules и audit. Повторный request с тем же idempotency key не создаёт дубликаты.
F-EXP-03. CSV/Excel-ячейки из пользовательского текста обезвреживаются от formula injection. PDF шрифты встроены, таблицы не обрезаются, карты имеют атрибуцию; русский текст проверен рендером. Синтетические/оценочные показатели и отсутствующие данные не теряют маркировку при экспорте.

## 22 Интерфейс и визуальное качество
Основной язык русский; строки через i18n-слой, чтобы позже добавить казахский без переписывания. Локальная дата/валюта, единообразные единицы, понятные названия. Рабочие экраны: обзор/карта, проблемы, приоритеты/программа, проект участка, сравнение, каталог, уход/исполнение, импорт/качество, справочники, источники/версии, администрирование. Чат как боковая панель сохраняет контекст карты.
Дизайн-система Claude: цвета по семантике, типографика, плотность таблиц, spacing, иконки, легенды, controls, focus/disabled/validation. Цвет не единственный носитель статуса. Основные действия доступны клавиатурой; focus order, labels и contrast WCAG AA как целевой уровень. Полноценное отдельное WCAG-сертифицирование не заявляется без аудита.
Карта занимает основной экран; панели могут сворачиваться и менять ширину. При выборе строки подсветить объект, при выборе объекта строку. Фильтры сохраняются в URL/сессии. Большие таблицы виртуализированы и имеют server pagination. Числа и графики показывают дату/горизонт и источник по раскрытию, без перегрузки первого экрана техническими терминами.
Состояния каждой функции: loading, empty, success, partial, unavailable, error, stale, forbidden и conflict где применимо. У ошибки есть действие повторить/исправить/открыть детали. Нельзя выводить бесконечный spinner без timeout или зелёный success после неуспешного сохранения. Скелетон не должен имитировать реальные числа.
Desktop основная среда: 1440x900, 1920x1080; tablet 1024x768; mobile 390x844 для просмотра, заданий и осмотров. Сложное точное 3D-редактирование может требовать desktop с явным объяснением, остальные маршруты не должны ломаться на телефоне. Горизонтальная прокрутка всей страницы недопустима; таблицы имеют собственный scroll.
Качество сдачи UI: все основные кнопки подключены; никакие карточки не содержат случайных постоянных KPI; моковые данные не смешиваются с production; смысловая анимация 150-250 ms, поддержка reduced motion. Визуальный review минимум всех основных экранов и состояний на указанных размерах, screenshots и найденные исправления в evidence.

## 23 API и согласование двух реализаций
Canonical контракт находится в contracts/openapi.json; типы общего домена в contracts/domain.schema.json. Этот пакет задаёт стартовый набор интеграционных операций. Любое расширение реализуется через общий контракт до зависимого UI. Реализованный API должен сохранять его смысл и не вводить несовместимые status/enum/units.
JSON по UTF-8; ошибки application/problem+json: type, title, status, detail, code, request_id, field_errors и blockers где применимо. 401 без сессии, 403 недостаточно прав, 404 недоступный/неизвестный объект по политике disclosure, 409 state/idempotency conflict, 412 ETag conflict, 422 входы/ограничения, 429 лимит, 503 временная недоступность. Стек-трейсы и секреты не возвращать клиенту.
GET collections: city_id, cursor, limit 1..200 default 50; bbox и фильтры по контракту. Stable cursor учитывает сортировку и набор фильтров; в ответе next_cursor и items. Не выдавать полный городской слой списком без ограничений. Денормализованные карточки имеют revision/version и updated_at, чтобы не смешивать результаты разных запросов.
POST, создающие ревизии, jobs, программы, proposals, exports и completions, требуют Idempotency-Key. Область ключа: user+route+resource; хранить request hash и первоначальный ответ минимум 24 часа. Повтор с другим телом - 409. Результат, который пользователь уже сохранил, не дублируется при повторе после обрыва сети.
Синхронный быстрый расчёт допускается для подбора+сметы; тяжёлые операции POST -> 202 Job. GET /jobs/{id} возвращает state и progress. SSE /jobs/{id}/events с event id и resume cursor; polling fallback с backoff. Процент прогресса не придумывать, если известны только фазы. Cancel cooperative, итог cancelled или succeeded если завершение опередило отмену; никаких наполовину опубликованных результатов.
Контрактные fixtures имеют synthetic=true и используются в dev/test MSW. Серверные и клиентские тесты валидируют один набор; generated client воспроизводим командой и не содержит ручных правок. Контрактная проверка не заменяет end-to-end тест с БД и workers.

## 24 Очереди транзакции и воспроизводимость
Создание job и outbox event - одна DB transaction. Dispatcher доставляет event at-least-once; worker deduplicates по job_id/input hash, получает lease и heartbeat. Job result сохраняется атомарно; запись результата и event completed согласованы. Не предполагать exactly-once transport. Повторный worker не удваивает строки сметы, задания или результаты.
Статусы queued/running/succeeded/failed/cancel_requested/cancelled. Lease истёк - requeue только для идемпотентной операции с ограничением attempts; необратимые side effects требуют отдельного guard. Внешний провайдер: timeout, retry только transient с exponential backoff+jitter и max attempts. Ошибки валидации/прав не retry бесконечно.
Outbox и jobs имеют version, created/started/completed timestamps, attempt, error_code, input refs, result refs и trace_id. Redis loss не теряет долговременные jobs: reconcile по DB. Файлы пишутся во временный ключ, затем manifest публикуется, orphan cleanup по TTL. При отмене/сбое незавершённый artifact не доступен как готовый.
Snapshot достаточен для повторения: исходные версии сохраняются, версия кода/образа известна, seed и параметры записаны. Повторение детерминированного расчёта совпадает в установленном допуске; аппаратно-зависимые физические модели имеют документированный tolerance. Один только hash без данных не является воспроизводимостью.

## 25 Безопасность эксплуатация и внешние зависимости
HTTPS и same-origin frontend/API. Secure HttpOnly cookies, session rotation, logout/revoke, CSRF, ограниченный CORS, CSP и security headers. Сервер проверяет город, grants, роль и ownership результата на каждом доступе, включая SSE, tiles, imports и exports. Массовый IDOR тест обязателен.
Секреты из environment/secret store, .env.example без реальных значений, secret scanning в CI. Ограниченные upload MIME/размер/распаковка; изоляция парсеров KML/ZIP и запрет внешних сущностей/SSRF. SQL параметризован; пользовательские выражения не выполняются как Python/SQL. Audit append-only с доступом admin, минимум actor/action/object/version/timestamp/reason.
Логи содержат trace/job IDs и коды, но не токены, полные prompts с restricted-геоданными и персональные сведения. Сроки хранения служебных аккаунтов/аудита/бэкапов согласуются с владельцем; проектное default для диагностических логов 30 дней, audit 365 дней, не выдавать эти сроки за юридическую норму. Персональные данные граждан не собираются.
Бэкапы БД ежедневно плюс WAL/PITR, объектное хранилище с версионностью и отдельной копией. Проектные цели RPO <=24 часа, RTO <=4 часа для стартового развёртывания; перед эксплуатацией выполнить восстановление в чистое окружение и измерить. Согласованная копия включает manifests и файлы, а не только SQL dump.
Миграции expand/contract, один migration owner, upgrade проверяется на копии. Перед destructive migration план backup/rollback и согласование по рабочему процессу; автоматический downgrade с потерей данных не является безопасным rollback. Сборка immutable, зависимости/образы закреплены, лицензии и уязвимости проверяются.
Карта может работать без платного API, но сервер/хранение/обработка имеют стоимость. OSM/Overture атрибуции и ODbL учитывать по слоям; PMTiles не скачивать bulk из публичных OSM тайлов. Open-Meteo free API некоммерческий; production terms уточнить. Внешние источники имеют cache, health, квоты и дату последнего успешного обновления. Live API недоступен - показывается сохранённая версия с датой, не исчезает весь продукт.

## 26 Производительность и измеримый стенд
P-01. Карта города готова к взаимодействию <=5 с p95 при холодной загрузке согласованного набора. P-02. Подбор растений и смета выбранной зоны <=5 с p95; время включает API и отображение результата, а не только серверный function timer. Не возвращать 202 мгновенно и считать это выполнением P-02. Источник этих ограничений - исходное ТЗ; метод p95 и стенд - уточнение этого документа.
Стартовый стенд: 50 000 зданий, 100 000 объектов зелени, 1 000 плановых зон, 500 вариантов каталога; 5 одновременно работающих специалистов, 20 viewer sessions. Это выбранный тестовый масштаб, не измеренная инвентаризация города. Сервер начальная конфигурация 8 vCPU/16 GB RAM/NVMe, клиент 4 CPU cores/8 GB RAM/WebGL2, 1440x900, сеть 20 Mbit/s RTT 50 ms. Hardware и actual results записать; конфигурация может быть изменена через ADR с повторным тестом, не ослабляя исходный <=5с.
P-03. Обычный read API p95 <=500 ms при стенде, сохранение ревизии <=1 с; не включает физические job. P-04. 3D участок до 2 000 видимых instanced посадок и 5 000 зданий после LOD: median FPS >=30, p95 frame time <=50 ms на согласованном GPU. Первый проход исследования на software renderer не является такой приёмкой. Target должен быть испытан на реальном устройстве демонстрации.
P-05. Городская оптимизация 1 000 зон x до 3 альтернатив имеет time budget 60 с; возвращает best feasible и gap либо честный timeout/infeasible. Физические расчёты имеют фазы, cancel и ресурсный budget, отдельный benchmark, без обещания универсальных 5 с. Смена простого UI состояния/выделения <=100 ms без network block.
Измерение: минимум 30 независимых повторов cold/warm отдельно, 10 минут устойчивой нагрузки, записать payload sizes, browser/device/network, version/hash, traces, error rate и memory. Стремиться к error rate <1% на валидных запросах. Smoke test не подменяет эти проверки. По результатам - оптимизация тайлов, spatial indexes, кеша и batch operations, а не подмена данных меньшим красивым примером без подписи.

## 27 Проверка качества и критерии приёмки
AC-01 Данные: импорт каждого формата с валидным и ошибочным примером; quarantine/publication; CRS и единицы; отчёт понятен; опубликованная версия восстанавливается. AC-02 Карта: город/районы/слои, адрес и полигон, provenance, legend; не загружается область вместо города; offline cold start по выбранному профилю.
AC-03 Подбор: запрещённый аллерген/ядовитый вид для соответствующей зоны исключён; unknown critical требует review; top-N объясняется; locks и разнообразие соблюдаются. AC-04 Сценарии: изменение сохраняет новую ревизию, stale result обозначен, 412 не теряет правки; повтор с idempotency key не дублирует.
AC-05 Деньги: ручной контрольный расчёт совпадает по строкам и rounding; отсутствующая ставка не ноль; reserve/замены не удвоены. AC-06 Survival: вероятности и исходные когорты корректны, источники/uncertainty видны; экспертная/ML-проверка задокументирована по DR-04. AC-07 Уход: вода и часы совпадают с операциями; невыполнимый план выявлен.
AC-08 Программа: решение удовлетворяет всем ограничениям; маленький набор совпадает с полным перебором; feasible/optimal различимы; ручное изменение валидируется. AC-09 Эффект: все показатели 5/10/20 представлены с единицами; покрытие union, потоки и stocks различены; air/LST/shade не смешаны; непройденная калибровка видна.
AC-10 3D: объекты совпадают с 2D, мерность верна, сервер блокирует конфликт; before/after одинаковая камера, время отдельно от возраста; placeholder heights помечены. Аналитические тени проверены на плоскости/столбе и эталонной городской геометрии с согласованным tolerance.
AC-11 Исполнение: созданное задание переживает reload/restart; partial completion и corrections сохраняются; осмотр исходной когорты отличается от замен. AC-12 Чат: инструменты соблюдают права, structured fact references точны, hallucination при missing inputs не проходит, proposal не меняет чужую ревизию.
AC-13 Экспорт: PDF/Excel и карточка совпадают по snapshot; текст/таблицы читаемы; licenses и assumptions сохранены. AC-14 Security: роли/grants, IDOR/CSRF, secrets, upload abuse, provider injection и download access проверены. AC-15 Operations: чистый compose launch, миграция, restore, worker crash/retry/cancel, Redis/provider outage.
AC-16 UX: обязательные маршруты на трёх размерах, все значимые состояния, клавиатура, отсутствие мёртвых кнопок и немаркированных моков. AC-17 Performance: P-01..P-05 с доказательствами. AC-18 Organizer acceptance: демонстрация на предоставленных данных и подтверждённом участке, описание моделей/архитектуры, код, README, отчёт, инструкция специалисту <=1 страницы.
Unit tests покрывают предметные инварианты, integration - PostgreSQL/PostGIS/queue/storage, contract - schemas и DTO, e2e - UI с реальным сервером, scientific - известные эталоны и локальную применимость. Не устанавливать красивый процент code coverage вместо этих проверок. Тесты не должны лишь повторять реализацию и подтверждать собственные допущения.
Release blocker: потеря/перепутывание данных или прав, выдуманные production-числа, неверные единицы, опасный hard-constraint bypass, незаметная смена ревизии, недостоверный claimed accuracy, сломанный основной маршрут. Непройденный data gate явно препятствует соответствующей профессиональной приёмке даже при работающем интерфейсе.

## 28 План разработки и параллельная работа
Этап foundation: WP-00 аудит стека/контрактов и общий bootstrap; WP-01 серверный каркас/БД/auth; WP-02 дизайн-система и UX states. WP-02 может идти параллельно WP-00/01, но API integration зависит от freeze контрактов. Не начинать две независимые реализации domain DTO.
Далее WP-03 ingestion/provenance и WP-04 карта; затем WP-05 расчётное ядро/scenarios и WP-06 редактор/сравнение; WP-07 программа/оптимизация; WP-08 физика/экология; WP-09 уход/исполнение; WP-10 ассистент/отчёты; WP-11 эксплуатация/нагрузка/качество. Номера отражают зависимости, а не требование ждать завершения всего этапа другим агентом.
Реальные зависимости, owner, deliverables, acceptance_ids и integration milestones заданы planning/work_packages.json. Задача done только после review, проверки на общем commit и evidence. Первый сквозной инкремент: вход -> published city dataset -> реальная зона из API -> сохранённая scenario revision -> детерминированная смета -> reload с тем же результатом.
Никакой срок не является основанием объявить невыполненный модуль «готовым MVP». При ограничениях явно показывать текущую готовность, а конечный объём сохранять. Улучшения архитектуры возможны через ADR с последствиями для контрактов и проверок.

## 29 Исследовательские задания и условия данных
DR-01: официальная граница, рабочие зоны и четыре набора организаторов. DR-02: локальный каталог и безопасность видов, питомники/доступность. DR-03: почвы, коммуникации, юридически применимые ограничения и правила. DR-04: история посадок, эксперт и протокол валидации. DR-05: реальные расценки, вода и бригады. DR-06: высоты, рельеф, климат, спутниковые/экологические коэффициенты. DR-07: эксплуатация, внешние API, лицензии и разрешение на обработку служебных данных. DR-08: лицензированный локальный адресный реестр с provenance и обновлением.
Пользователь может передать исследовательскому агенту prompts/RESEARCH_DATA.txt. Результат исследования - файлы/ссылки+лицензии+даты+метод+схема+sample+quality report, а не пересказ сайтов. Исследователь не придумывает недоступные значения и не контактирует с людьми без отдельного поручения. Официальный статус правовой нормы и действующая редакция проверяются по первоисточнику; конкретные отступы не зашиваются по случайной статье.
До DR-01 можно реализовать ingestion на маркированных fixtures и открытом городском контуре; до DR-02/03 автоматическое approved placement блокируется; до DR-04 survival помечается как экспертная/неоткалиброванная оценка; до DR-05 нет окончательной реальной сметы; до DR-06 нет claims о точном городском микроклимате; до DR-07 production egress/размещение не утверждено; до DR-08 локальный address autocomplete честно недоступен и участок выбирается на карте.
Отсутствие данных не означает отказ от продукта. Строятся полноценные механизмы, источники открытых данных и корректные unavailable-состояния; отдельно согласуется профессиональная пригодность результатов. Все данные и допущения проходят тот же реестр версий.

## 30 Поставка и определение готового продукта
Поставка: исходный код в этом репозитории, закреплённые зависимости, migrations, compose, README quickstart, безопасный .env.example, versioned manifests и лицензии, тестовый профиль, production deployment guide, backup/restore runbook, API contract/client, тесты и результаты, образец PDF/Excel, инструкция специалисту <=1 страницы, архитектурная схема и known limitations.
Чистый запуск должен быть одной документированной командой после установки Docker и конфигурации секретов. Нельзя требовать ручного редактирования БД или скрытого набора файлов автора. Offline-city bundle строится отдельной воспроизводимой командой из разрешённых данных; его состав и checksum известны.
Definition of Done продукта: AC-01..AC-18 проверены в применимой части; data gates для заявленных профессиональных результатов закрыты; не осталось критических/высоких дефектов; UI реально связан с API; данные сохраняются и восстанавливаются; роль/grants соблюдены; справочники и модели имеют источники; опыт специалиста подтверждён сквозным сценарием. Если gates открыты, выпуск называется технически готовой платформой с конкретными ограничениями, а не полностью подтверждённым муниципальным решением.
ТЗ и контракты версионируются вместе с кодом. В scope-change записывать что изменилось, почему, какие acceptance tests затронуты. Работа обоих агентов проверяется по одному набору критериев; количество файлов, агентов и красивых анимаций не является показателем готовности.
