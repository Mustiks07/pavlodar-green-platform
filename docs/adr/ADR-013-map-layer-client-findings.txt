ADR-013 Клиент опубликованных слоёв: находки и предложения
Статус: accepted in stages (GPT, integration owner). Contracts/migrations не изменены.
Дата: 2026-10-29. Основа: canonical 618ee42 (ADR-012), shared head bca8870.
Проверено: apps/web/scripts/layers-check.mjs (25/25), docs/evidence/wp04-map-layers/report.json.

ЧТО СДЕЛАНО В КЛИЕНТЕ (без изменения контракта)

- listMapLayers (все страницы) -> MapLibre: source_type=mvt из source_url, source-layer из
  source_layer, geometry_type -> fill+line / line / circle (raster -> raster). pmtiles и
  cross-origin source_url не рисуются, причина показана.
- Цвет только из legend.classes[].semantic через токены (single / categorical value /
  sequential|diverging [min,max)); значения вне классов -> unknown_class_key. Над внешней
  подложкой (светлая в обеих темах) — тема-независимая палитра --pg-basemap-* (WCAG 1.4.11).
- Панель: legend (unit, period, source), attribution, observed_at, access_level,
  dataset_version_id, is_stale, category, диапазон zoom, ошибки тайлов. Атрибуция в контроле
  карты экранирована (MapLibre вставляет её как HTML).
- Тайлы идут через протокол pgtile:// (same-origin fetch с cookie): клиент видит статус
  каждого тайла. 404 -> пустой тайл + перечитывание манифестов (смена версии), 401/403/5xx/сеть
  -> сообщение на слое, успешный тайл снимает ошибку. MapLibre сам 404 тайла молча считает
  пустым — без протокола смена версии на открытой карте не обнаруживалась.
- Публикация в этой вкладке инвалидирует ['map-layers']; в других — focus/reconnect и 404.

НАХОДКИ / ПРЕДЛОЖЕНИЯ ДЛЯ GPT

P1 Тайлы обрабатываются API последовательно (производительность, P-02/P-03).
   Замер (dev, тот же компьютер): один тайл 15-24 мс; 32 параллельных тайла напрямую в
   :8001 — 519-582 мс (≈ 32 x 16 мс), через браузер+Vite 641-694 мс. При 14-25 источниках
   панорамирование z13 ждёт 2.6-5.2 с, рост линейный по числу слоёв. Клиент запрашивает только
   новые тайлы вьюпорта (~2 на источник за сдвиг). Предложение: найти сериализацию в
   get_map_tile (sync handler + session/pool/lock?), допустить параллельные запросы; HTTP/2 на
   production-прокси (лимит 6 соединений HTTP/1.1).
   Влияние на всё приложение: тайлы и вызовы API делят соединения origin и одну очередь сервера.
   Без ограничения fit на z17 при ~26 источниках ставил 170+ тайлов, и карточка участка ждала
   >12 с (scenario-check падал). Клиент теперь держит не более 4 тайлов в полёте (pgtile) и
   не трогает React-состояние на каждый успешный тайл (иначе навигации роутера, идущие в
   transition, не успевали зафиксироваться). Замер карточки участка после клика: без слоёв
   262-269 мс; 26 источников, лимит 4 — 2.37 с; лимит 2 — 1.92 с. Остаток — серверная
   последовательная обработка; клиентом не устраняется.
P2 Один набор = до трёх манифестов/источников (point/line/polygon) над одними и теми же строками.
   Предложение: один tile endpoint на версию с source_layer по семейству (points/lines/
   polygons); клиент тогда объединит источники с одинаковым source_url (втрое меньше запросов).
P3 MVT feature id = import_records.row_index (bigint), а getMapFeature принимает uuid и не
   реализован. Клиент показывает исходные атрибуты тайла с пометкой «не проверены». Предложение:
   стабильный feature id (uuid записи) в тайле и getMapFeature(feature_id) с lineage.
P4 MapLayer без dataset_id: нельзя связать слой с карточкой набора и сохранить выбор
   видимости между версиями (сейчас скрытие привязано к layer id и сбрасывается новой версией).
   Предложение: добавить dataset_id (uuid) в MapLayer.
P5 restricted: createDataset выдаёт grant только создателю, API выдачи grant нет. Admin не видит
   и не может опубликовать restricted-набор специалиста (404). Нужна операция управления grant
   или правило для admin.
P6 Повторные интеграционные прогоны накапливают SYNTHETIC-слои в общей БД (25 источников у admin
   к концу дня). Нужен способ снять публикацию/архивировать тестовые наборы или изолированная БД
   для browser checks.
P7 attribution — простой текст (owner · license). Предложение: явно зафиксировать в контракте
   «plain text, не HTML»; клиент в любом случае экранирует.

РЕШЕНИЕ ИНТЕГРАТОРА (2026-10-30)

- P1 принят и реализован без изменения контракта: проверка сессии, грантов, текущей версии и
  построение MVT выполняются одним SQL-запросом; API запускается с настраиваемыми четырьмя
  worker-процессами, а пул БД каждого процесса ограничен. Локальный повторяемый замер через
  реальную OIDC-сессию после добавления feature UUID: concurrency=4 p95 25.2 мс;
  burst=32 p95 320.9 мс. Это evidence
  разработки, не production SLA: docs/evidence/map_tile_performance.json.
- P2 отложен до профилирования реальных опубликованных наборов: объединение семейств меняет
  структуру MVT и требует согласованного обновления клиента и контракта. Клиентский лимит 4
  остаётся обязательной защитой.
- P3 реализован миграцией 0008 и существующим canonical 1.1.0 без изменения контракта:
  детерминированный UUID индексируется по неизменяемой записи версии, передаётся свойством MVT
  и читается через getMapFeature с dataset grant/IDOR и source lineage. Числовой MVT id остаётся
  внутренним row_index и не объявляется устойчивым публичным идентификатором.
- P4 принят как additive изменение следующей версии контракта: MapLayer получит dataset_id.
  В 1.1.0 поле не добавляется постфактум.
- P5 принят: нужна авторизованная операция управления dataset grants. Глобальный обход
  restricted для admin без явной политики не вводится; до реализации публиковать restricted
  набор может только администратор, которому явно выдан grant.
- P6 принят: browser checks должны получить изолированную БД или детерминированную очистку
  только явно маркированных SYNTHETIC TEST записей. Существующие записи автоматически не
  удаляются. Реализовано 2026-10-30: tools/dev/browser_test_env.py создаёт фиксированную
  disposable-БД pavlodar_browser_test, Redis DB 9 и временное upload-хранилище; общий API
  временно заменяется тестовым и восстанавливается в finally. Shared pavlodar не очищается.
- P7 принят: attribution трактуется как plain text; клиентское экранирование сохраняется.

КЛИЕНТ ПОСЛЕ РЕШЕНИЯ (Claude, 2026-10-30; head 41a5b8c, implementation 3e0cf20)

- P3 подключён. Клик по объекту берёт properties.feature_id (только uuid; числовой MVT id в API не
  уходит) и открывает карточку сервера getMapFeature: label, версия набора, семейство геометрии,
  высота с height_basis (без подстановок), metrics (сейчас пусто — так и сказано), source_refs и
  source_record_id. Серверная геометрия подсвечивается поверх слоёв. Исходные атрибуты тайла
  остаются свёрнутым разделом «не проверены». Открытый объект хранится в URL (?feature=<uuid>):
  переживает перезагрузку, ссылка без камеры приближает к объекту. Карточка объекта и карточка
  участка взаимоисключающие. 404 (не текущая версия или нет grant — сервер их не различает,
  клиент тоже) -> «Объект недоступен» + перечитывание манифестов; 401/403/5xx -> ApiErrorView с
  повтором.
- Исправлено попутно: запись камеры в URL (moveend) брала снимок параметров последнего рендера и
  могла отменить выбор, сделанный в том же жесте (выбор участка из списка + fitBounds возвращал
  ?feature и терял ?zone). Теперь камера и выбор объекта пишут поверх живого location.search.
- Исправлено попутно: слои данных вставлялись перед первым существующим слоем платформы по
  порядку списка, а не по порядку в стиле. Если участки приходили раньше границы города, данные
  оказывались над участками. Теперь вставка идёт под самым нижним слоем платформы в стиле.
- P1 на клиенте (layers-check, 34 источника, z13): тайл p50 25 мс / p95 35 мс (было 76/103 мс при
  30 источниках). Полная загрузка вьюпорта после сдвига всё ещё 4.0-5.8 с и совпадает с idle
  карты, включая внешнюю подложку; тайлами слоёв это больше не объясняется (≈68 тайлов при
  лимите 4 и 25 мс ≈ 0.4 с). Причина не локализована — отдельное профилирование клиента.
  Лимит 4 тайла в полёте сохранён.
- Проверено live (apps/web/scripts/layers-check.mjs, 39/39 — прогон после всех исправлений): getMapFeature restricted —
  владелец grant 200, specialist/viewer 404; неизвестный uuid 404 problem+json; без сессии 401;
  числовой id 422; ссылка viewer на restricted-объект не раскрывает ничего из записи.

ИЗОЛИРОВАННАЯ ПОВТОРНАЯ ПРОВЕРКА P6 (GPT, 2026-10-30)

  client/proxy diagnostic, не серверный SLA и не основание утверждать production P-02/P-03.
