ADR-037: Версионированная нормализация городских приоритетов
Статус: принято
Дата: 2026-10-30

Контекст

Контракт 1.5 требовал normalization_version_id, но не позволял клиенту узнать допустимую
версию. Подстановка скрытого UUID в интерфейсе нарушила бы общий контракт. Кроме того,
доступные сейчас открытые слои не дают оснований придумывать локальные пороги жары,
населения, социальных объектов или экологических эффектов.

Решение

1. Аддитивный контракт 1.6 вводит listPriorityNormalizations и неизменяемое описание
   факторов, формулы, группы need/readiness и диапазона 0..1.
2. Первая версия f5f9b550-42ab-5bfd-bf5e-2c442ad5e254 использует только две доли,
   уже вычисляемые авторизованным ZoneContext:
   - green_deficit = 1 - clamp(existing_green_area / zone_area, 0, 1);
   - soil_coverage = clamp(soil_coverage_fraction, 0, 1).
   Границы 0 и 1 следуют из определения доли, а не из локальной калибровки.
3. Сервер принимает только факторы опубликованной версии, фиксирует веса и сохраняет
   PriorityResult в неизменяемой таблице migration 0019.
4. Если положительно взвешенный фактор неизвестен, общий и соответствующий групповой
   score равны null. data_coverage показывает долю известных весов. Неизвестность не
   трактуется как ноль и не влияет скрытым штрафом.
5. Результат доступен создавшему специалисту и администратору города. Это не раскрывает
   ссылки на закрытые наборы другим пользователям города.

Последствия

- UI может строить устойчивый выбор факторов без зашитого UUID.
- Результат воспроизводим по версии формулы, весам и исходным ссылкам.
- Текущая версия не заявляет официальную локальную калибровку и не включает отсутствующие
  population/heat/social/ecosystem факторы.
- CP-SAT может использовать только полностью рассчитанные benefit-факторы; неполные
  кандидаты должны завершаться явным blocker, а не искусственным score.
- Общая база остаётся на migration 0017 до завершения текущих проверок Claude. 0018 и
  0019 проверены в одноразовой тестовой БД и применяются совместно после её освобождения.
